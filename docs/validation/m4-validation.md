# Milestone 4 validation

The completed automated gate passed **152 Java tests and 36 Python tests**, together with Spotless, Ruff, frontend lint/type checks and the production frontend build. This document records verified scheduling and admission behavior. Backend and Worker Docker builds passed, and all three updated Agents and backend started healthy. The live backend-to-Agent checks passed; evidence is saved in [m4-scheduler-smoke.json](m4-scheduler-smoke.json).

Java integration tests use a fresh schema on the real MySQL 8 service rather than an in-memory substitute. `scripts/test-backend.sh` injects an owned Redis namespace and temporary filesystem roots, then removes only those test resources. Ordinary test contexts disable background scheduling; tests invoke the relevant services with controlled fixtures. Demo database contents and runtime cache keys stay separate.

Test sources: [resource reservations](../../backend/src/test/java/com/example/cae/resource/ResourceReservationIntegrationTest.java), [node registry](../../backend/src/test/java/com/example/cae/resource/NodeRegistryIntegrationTest.java), [resource profiles](../../backend/src/test/java/com/example/cae/resource/ResourceProfileIntegrationTest.java), [database scheduling](../../backend/src/test/java/com/example/cae/scheduler/SchedulerIntegrationTest.java), [selection policy](../../backend/src/test/java/com/example/cae/scheduler/NodeSelectionPolicyTest.java), and [submission/cancellation](../../backend/src/test/java/com/example/cae/job/submission/JobSubmissionIntegrationTest.java).

The gate also corrected two integration defects: Job option JSON was being serialized twice during command updates, and MySQL `DATETIME` values were not normalized from `LocalDateTime` to UTC strings before scoring. The stored-option submit test and three-candidate real-MySQL scheduler test exercise those paths.

The live smoke sends eight concurrent duplicate submit commands, then checks one durable execution, stable request/external IDs and a real independent Solver PID through successful completion. A separate running cancellation checks durable intent, the same process identity, confirmed CANCELLED at both ends, exactly restored license/node counters and an unchanged repeated cancel. All three nodes were ONLINE with reachable workspaces. Successful runtime remains backend SUBMITTED until the M6 monitor; no full-pipeline result is claimed in M4.

The Docker vfs guard initially stopped the Java build at 6,065 MiB against its 6,144 MiB reserve. Reclaiming an owned npm download cache and unused Docker build snapshots/dangling images resolved the build; containers, named images and volumes were preserved. The build guard now uses a 6 GiB Java reserve and 4 GiB Worker/frontend reserve based on their actual build sizes.

Deployment also revealed seven early M1 test Jobs with fabricated `current_execution_id=101`, left before the execution table existed. A backup at `/tmp/cae-m4-before-migration-repair.sql` captured the affected tables; each specific CREATED fixture received a repair audit before clearing its orphan reference. The half-created execution table was empty, so only that empty migration artifact and the failed V2 history entry were removed. V2/V3 then applied successfully with all existing Jobs/events/files preserved. The old test now exercises real metadata CAS without inventing foreign keys, and the isolated test wrapper prevents future demo database contamination.
