# Milestone 6 validation

The final gate passed 180 Java tests, 42 Python tests, Spotless/Ruff/ESLint, frontend type checks/build and the backend Docker build. The three Workers run the tested callback image; the rebuilt backend applied V5/V6 and started healthy. The real reconciliation smoke passed all five scenarios without a runtime script repair.

`ExecutionMonitoringIntegrationTest` uses an owned MySQL schema and a controlled HTTP Agent to verify identity checks, duplicate/out-of-order callbacks, poll lease ownership and expired-generation fencing, retained reservations on missing heartbeats or remote 404, recovery of the same accepted request, persistent cancellation intent, confirmed terminal release, and one parse command when completion wins cancellation. It also covers durable backfill of legacy completed executions without starting a Solver, and preservation of an observed RUNNING state across UNKNOWN recovery even when an older SUBMITTED response omits `startedAt`.

The Worker callback tests use actual independent processes and HTTP receivers to verify progress and terminal facts, service-token authentication, bounded retries, heartbeat independence, startup replay, redirect rejection, and bounded pagination. These tests do not claim that a HTTP process launch can be atomically committed with SQLite; uncertain launch windows remain UNKNOWN and never automatically launch another process.

The live `tests/e2e/reconciliation_smoke.py` script creates only its own Jobs and uses real local MySQL, RabbitMQ, backend, and Worker services. The committed [reconciliation smoke evidence](m6-reconciliation-smoke.json) records these actual outcomes:

- Job `CAE-20261011-000082`, execution 5 on node-a: a backend-only restart occurred while the 40-second Solver remained RUNNING. Worker container IDs, durable execution request/hash, external ID, PID, and process start identity were unchanged. The recovered Job returned to RUNNING and automatically reached POST_PROCESSING after actual SUCCESS.
- Job `CAE-20261011-000083`, execution 6 on node-b: a 60-second Solver and callbacks continued while heartbeat emission was disabled. The node became OFFLINE, and the Job remained UNKNOWN for six seconds despite explicitly submitted verified RUNNING callbacks. Resource/license counters stayed held. Heartbeat restoration recovered the same process, which later completed successfully and automatically reached POST_PROCESSING.
- Jobs `CAE-20261011-000084` and `CAE-20261011-000085`, executions 7/8: actual remote RUNTIME_FAILED and TIMEOUT mapped to `SOLVER_RUNTIME_FAILED` and `SOLVER_TIMEOUT`. Raw codes remained `MOCK_NUMERICAL_FAILURE` and `MOCK_TIMEOUT`, respectively; raw messages and exit codes matched the remote facts. Both reservations were RELEASED and neither Job produced a parse command.
- Job `CAE-20261011-000086`, execution 9: cancellation won the real cancellation/completion race. Both remote and backend states were CANCELLED; resources were RELEASED and no parse command was emitted. Repeated cancellation preserved the terminal state and Job version. The controlled integration test separately verifies the successful-completion-wins branch and its one parse command.
- The two successful executions each received repeated terminal callbacks yet retained exactly one committed `RESULT_PARSE_REQUESTED` event/command. Both Outbox commands were SENT after confirmation, and their delivery-mode-2 messages remained present in the actual parse queue, whose parser consumer is deliberately absent until M7. All license counters returned to their initial zero baseline. The historical M5 malformed-message DLQ payload remained readable before and after the restart; Worker containers and all shared volumes were preserved.

Review before the final gate found a recovery regression: a stale SUBMITTED response could replace an already observed RUNNING state after an intervening UNKNOWN state. V6 persists the running observation independently of optional Agent `startedAt`; the regression tests cover both callback and poll observations, including missing start time. The complete gate and live smoke passed after that repair.

M6 ends at durable parse dispatch. Result parsing and report completion are the M7/M8 acceptance gates.
